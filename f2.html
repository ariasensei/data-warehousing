Lecture 1 · Cloud Data Warehousing

A question that one spreadsheet cannot answer

Which campus bookstore branch earned the most this month?

  • Sales records are in different branch files.
  • Product categories are maintained in another system.
  • Repeated records and inconsistent dates distort the total.
  • A warehouse integrates clean, historical data for analysis.
MKDB teaching notes

Ask students how they would combine three branch spreadsheets. Which columns must match? What happens if one file repeats a sale?

Lecture 1

What is a data warehouse?

  • Subject-oriented: organized around sales, students, inventory, or another business subject.
  • Integrated: combines sources using consistent definitions.
  • Time-variant: keeps data useful for analysis over time.
  • Nonvolatile: primarily supports reading and controlled loading rather than continuous operational transactions.
MKDB teaching notes

Nonvolatile does not mean corrections are impossible. Governed pipelines can correct and refresh data. Historical requirements determine what must be retained.

A warehouse does not replace the checkout system. It answers a different kind of question.

Lecture 1

What changes when the warehouse is in the cloud?

  • Storage and processing run on a provider’s infrastructure.
  • Teams access governed data through network connections.
  • Capacity can scale without buying a physical server first.
  • Many platforms separate data storage from query compute.
  • Cloud services still need data modeling, access rules, and monitoring.
MKDB teaching notes

Compare renting a venue sized for an event with owning a permanent building. Renting can provide flexibility, but continued use still has a cost.

Lecture 1

Follow the data to the decision

POS files → Ingestion → Cleaning → Warehouse tables → SQL reports
  • Ingestion brings branch records into the platform.
  • Cleaning removes repeated records and validates values.
  • Warehouse tables store facts and descriptive dimensions.
  • Reports support decisions about stock and branch performance.
MKDB teaching notes

Trace one USB drive sale through the whole flow. The manager sees a category total, but that total must remain traceable to its source.

Lecture 1

Facts, dimensions, and grain

  • Fact: measurable event, such as a sale line.
  • Measures: quantity and revenue.
  • Dimensions: product, branch, and date describe the event.
  • Grain: exactly what one fact-table row represents.
  • For our lab: one row = one sale line. Never mix sale lines and daily totals in the same fact table.
MKDB teaching notes

Ask: if an order contains a notebook and a pen, is it one fact row or two? At sale-line grain, it is two. Our small dataset uses one line per sale ID.

Lecture 1

Security and responsible use

  • Give users only the access they need.
  • Separate raw sensitive records from reporting datasets.
  • Use fictional teaching data for this lab.
  • Keep access and change records; inspect data lineage.
  • Agree on definitions: Does revenue include returns, tax, or discounts?
MKDB teaching notes

Explain that accurate SQL can answer the wrong question if the business definition is wrong. Our lab revenue is quantity × listed unit price, excluding returns, taxes, and discounts.

Lecture 1

Cloud platforms and selection

  • Examples include Databricks SQL, Snowflake, BigQuery, and Amazon Redshift.
  • Compare workload, SQL needs, governance, integration, and total cost.
  • Choose based on the problem and operating environment.
  • In this course we use Databricks to practice warehouse concepts on lakehouse tables.
MKDB teaching notes

These are examples, not a ranking. Avoid teaching that any one platform is always the fastest or cheapest.

Lecture 2 · Big Data and Modern Data Warehousing

Why traditional workflows become difficult

A game studio records millions of player events, purchases, and support messages.

  • Events arrive throughout the day.
  • Logs and messages have different structures.
  • Analysts need trustworthy totals and long-term trends.
  • Engineers must distribute processing and maintain consistent rules.
MKDB teaching notes

Connect to students’ daily use of games and mobile apps. A player click is small, but the combined workload can be substantial.

Lecture 2

Warehouse, lake, and lakehouse

ArchitectureTypical strengthWhat still needs work
WarehouseStructured reporting and consistent business modelsSource integration and historical design
Data lakeFlexible storage for diverse raw dataQuality, discoverability, and governance
LakehouseLake storage with table management and analytics capabilitiesModeling, pipelines, permissions, and validation
MKDB teaching notes

These are architecture patterns with overlapping product features. A lakehouse does not automatically produce correct star schemas or clean data.

Lecture 2

Distributed processing

  • Split large datasets into partitions across workers.
  • Process portions in parallel, then combine results.
  • Joins and grouping may move data between workers: this is a shuffle.
  • More workers do not automatically solve poor joins or skewed data.
  • Our small lab teaches modeling; it is not a big-data performance benchmark.
MKDB teaching notes

Use teams totaling different piles of receipts. If one team receives nearly all the receipts, the other teams wait: this illustrates skew.

Lecture 2

Batch versus streaming

ApproachExampleTradeoff
BatchLoad all branch sales every nightSimpler; results arrive later
StreamingProcess purchases as events arriveFresher; late and repeated events need policies
MKDB teaching notes

Teaching prompt: Ask whether a monthly dean’s report requires second-by-second updates. Choose freshness based on business need.

Lecture 2

Bronze → Silver → Gold

Bronze: raw → Silver: validated → Gold: business-ready
  • Bronze keeps the ingested records for traceability.
  • Silver standardizes types and handles invalid or duplicate records.
  • Gold contains dimensions, facts, and reporting outputs.
  • Layers can be separate schemas or clearly named tables. Our lab uses one personal schema.
MKDB teaching notes

This is a design pattern, not a requirement to create exactly three physical folders. Reference: official Databricks medallion architecture documentation.

Lecture 2

Delta tables and reliable processing

  • Delta Lake adds transaction and table-management capabilities to lake storage.
  • Transactions help avoid partially committed table writes.
  • Table schemas help control the expected structure.
  • Version history can support auditing and recovery within retention limits.
  • Data quality rules remain your responsibility.
MKDB teaching notes

Avoid promising permanent time travel. Available history and files depend on retention and maintenance. The lab uses USING DELTA explicitly.

Lecture 2

Modernization means more than faster queries

  • Incremental loading processes new or changed records.
  • Orchestration schedules tasks in dependency order.
  • Observability detects failures, delays, and unusual row counts.
  • Governance records who can access data and where it came from.
  • Semantic definitions keep measures consistent across reports.
MKDB teaching notes

Our introductory script performs full rebuilds. A production pipeline would need incremental logic, business keys, handling of corrections, and history policies.

Lecture 2

When data arrives twice or arrives late

  • A retry can repeat the same sale; blindly adding it doubles revenue.
  • An event for yesterday may arrive after today’s report is built.
  • Use a stable event key and explicit duplicate rules.
  • Define when reports refresh and how late events update history.
  • Conflicting records need a policy; DISTINCT removes only exact duplicates.
MKDB teaching notes

Ask: Should a changed price overwrite yesterday’s sale? Historical facts should reflect the agreed business rule, not an accidental join to today’s product price.

Lecture 2

Knowledge check

  • Why is storing every file in one lake insufficient for reliable reporting?
  • Which medallion layer should preserve an invalid source record?
  • When would batch processing be sufficient?
  • Why is one repeated transaction a business problem?
MKDB teaching notes

Possible answers: integration and quality still needed; bronze retains source and a rejection table isolates invalid rows; periodic reporting often suits batch; totals become inflated.

Lab · Setup

Compute is different from stored data

A SQL warehouse is the engine, not the shelf.

  • The compute selector connects your query to a SQL warehouse.
  • Your tables are registered under catalog.schema.table.
  • Managed Delta tables store data in platform-managed storage.
  • Stopping query compute does not delete the warehouse tables.
  • Our warehouse is a logical model built from these tables and views.
MKDB teaching notes

Example: workspace.dw_basa.fact_sales is a table name only if workspace is a real writable catalog in your account. Do not assume this catalog name exists.

Open and connect the SQL editor

  • Open SQL Editor from the sidebar.
  • Use the + / Create new query control to create a query.
  • Name it DW_FirstWarehouse_YourName.
  • Select an available SQL warehouse near the top of the editor.
  • Paste one numbered section from the supplied SQL, select it, and click Run. Repeat in order.
MKDB teaching notes

If no warehouse appears, check access with the instructor or administrator. Do not direct students to create a paid service merely to complete the lab.

Lab · Step 1

Choose a writable catalog and schema

SHOW CATALOGS;
SELECT current_catalog(), current_schema();
-- Only if needed; replace with an actual catalog:
-- USE CATALOG `your_writable_catalog`;
CREATE SCHEMA IF NOT EXISTS dw_surname;
USE SCHEMA dw_surname;

Replace surname with your own unique identifier. Use a writable catalog, not samples or a system catalog.

MKDB teaching notes

On a managed workspace, schema creation needs USE CATALOG and CREATE SCHEMA. If the instructor supplies an existing schema, skip CREATE SCHEMA and use that schema. CREATE TABLE and USE SCHEMA privileges are needed for subsequent steps.

Lab · Step 2

Load and inspect the raw data

  • Run section 2 of the SQL file to create bronze_sales.
  • Open Catalog → chosen catalog → personal schema → bronze_sales.
  • Inspect columns and the data preview, or run SELECT * FROM bronze_sales.

MKDB teaching notes

Our business rule excludes returns from this sales lesson. Negative quantity is invalid under that rule; real retail systems often model returns separately.

Lab · Step 3

Clean without hiding the problems

  • Run section 3 to build rejected_sales and silver_sales.
  • Convert the date string to DATE and the unit price to DECIMAL.
  • Keep invalid rows in rejected_sales.
  • Remove the exact duplicate using SELECT DISTINCT.
  • Expected: 1 rejected row and 7 clean rows.
MKDB teaching notes

Ask students to explain why rejected data should be inspected rather than simply disappearing. A conflicting S007 with another price would not be fixed by DISTINCT alone.

Lab · Step 5

Validate before reporting

  • Run section 5. Compare bronze, rejected, silver, and fact row counts.
  • Check duplicate sale IDs: expected no rows.
  • Check unmatched dimension keys: expected no rows.
  • Check total revenue: expected ₱1,575.00.
  • Reconciliation: 9 raw − 1 invalid − 1 duplicate = 7 fact rows.
MKDB teaching notes

Dimension rows must be unique on their keys. A duplicated dimension key can multiply joined facts. These checks are useful even when tables are successfully created.

Save a reusable report
