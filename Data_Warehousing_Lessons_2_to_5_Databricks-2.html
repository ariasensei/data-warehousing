LESSON 2

Data Quality and
Data Cleansing

Reliable analysis begins with reliable data.

02

Data quality in simple terms

Data has quality when it is correct, complete, consistent, and suitable for its purpose.

Operational data

  • Supports daily transactions
  • Changes frequently
  • Example: recording one sale

Analytical data

  • Supports reports and decisions
  • Often includes historical records
  • Example: comparing yearly sales
GIGO: Garbage In, Garbage Out. Poor input produces unreliable reports.

Seven dimensions of data quality

DimensionQuestionExample
AccuracyIs the value correct?Quantity is 5, not 50.
CompletenessAre required values present?Product is not NULL.
ConsistencyDo values follow one standard?Use “Electronics” everywhere.
ValidityDoes the value follow a rule?Quantity must exceed zero.
UniquenessIs each record represented once?One row per sale ID.
TimelinessIs the data available when needed?Today’s sales appear today.
IntegrityDo related records connect correctly?Every sale uses a valid customer ID.

Common data quality problems

Missing

NULL date or product

Repeated

Duplicate sale ID

Invalid

Negative quantity

Inconsistent

Electronic vs. Electronics

Incorrect type

Text stored in a number column

Unusual value

An extreme price or quantity

Look at sales_raw: Which problems could change the total revenue?

Data profiling finds problems

-- Table structure
DESCRIBE sales_raw;

-- Missing values
SELECT
 SUM(CASE WHEN sale_date IS NULL THEN 1 ELSE 0 END) missing_dates,
 SUM(CASE WHEN product IS NULL THEN 1 ELSE 0 END) missing_products
FROM sales_raw;
-- Duplicate IDs
SELECT sale_id, COUNT(*) records
FROM sales_raw
GROUP BY sale_id
HAVING COUNT(*) > 1;

-- Distinct spellings
SELECT DISTINCT category, status
FROM sales_raw;

Data cleansing process

Profile›Define rules›Correct›Remove duplicates›Validate›Document

Possible rules

  • Quantity must exceed zero.
  • Every sale needs a date.
  • One sale ID represents one transaction.
  • Category names use approved values.
Business meaning matters.

Never delete or replace a value simply because it looks unusual. Confirm what the field means and how the organization uses it.

Missing data requires judgment

MethodWhen it may work
Delete the rowThe record is unusable and only a small number are affected.
Mean or medianA missing numeric value needs a reasonable estimate.
ModeA missing category can use the most common value.
“Unknown”The value matters, but the true value cannot be recovered.
Recover from a sourceA reliable system contains the correct original value.

Would you replace a missing student grade with zero? Explain the effect on the student and the class average.

Standardization and validation

Standardization

  • electronic → Electronics
  • complete → Completed
  • Convert dates to YYYY-MM-DD
  • Use one measurement unit
  • Apply consistent capitalization

Validation

  • Range check: quantity > 0
  • Format check: valid email or date
  • Type check: price is numeric
  • Required-field check
  • Referential integrity check
  • Business-rule check

Create a cleaned Delta table

CREATE OR REPLACE TABLE sales_clean AS
WITH prepared AS (
 SELECT *, ROW_NUMBER() OVER(PARTITION BY sale_id ORDER BY sale_id) rn
 FROM sales_raw
)
SELECT
 sale_id,
 COALESCE(TRY_CAST(sale_date AS DATE), TRY_TO_DATE(sale_date,'yyyy/MM/dd')) sale_date,
 COALESCE(TRIM(product),'Unknown') product,
 CASE WHEN LOWER(TRIM(category)) IN ('electronic','electronics')
      THEN 'Electronics' ELSE INITCAP(TRIM(category)) END category,
 INITCAP(TRIM(city)) city, quantity, unit_price,
 CASE WHEN LOWER(TRIM(status)) IN ('complete','completed')
      THEN 'Completed' ELSE INITCAP(TRIM(status)) END status,
 quantity * unit_price total_amount
FROM prepared
WHERE rn=1 AND quantity>0 AND unit_price>=0
 AND COALESCE(TRY_CAST(sale_date AS DATE),TRY_TO_DATE(sale_date,'yyyy/MM/dd')) IS NOT NULL;

LESSON 3

OLAP and
Multidimensional Analysis

Explore warehouse data from different perspectives.

03

OLAP answers analytical questions

Online Analytical Processing supports fast, flexible analysis of historical data.

OLTP

  • Records daily transactions
  • Uses current detailed data
  • Example: save one sale

OLAP

  • Finds trends and comparisons
  • Uses detailed and summarized data
  • Example: compare monthly sales

Which city earned the most? Which category improved? These are OLAP questions.

Facts, measures, and dimensions

ConceptMeaningSales example
FactA business eventA completed sale
MeasureA numeric value for analysisQuantity or total amount
DimensionA viewpoint for organizing factsProduct, time, or city
HierarchyRelated levels in a dimensionYear, quarter, month, day
GranularityThe level of detailOne row per transaction

The data cube

A data cube organizes a measure using several dimensions.

  • Measure: total sales
  • Product: Laptop, Keyboard, Chair
  • Time: Month or year
  • Location: Manila, Makati, Cavite

Example question

What were the monthly sales of each product category in every city?

TIMEPRODUCTLOCATION

“Cube” is a concept. A model may contain more than three dimensions.

Five OLAP operations

OperationPurposeExample
Roll-upSummarize detailsMonth to year
Drill-downShow more detailYear to individual day
SliceSelect one dimension valueElectronics only
DiceFilter several dimensionsElectronics in Manila during Q1
PivotRearrange the viewpointTurn city values into columns

Roll-up and drill-down

-- Roll-up: monthly totals
SELECT
 YEAR(sale_date) year,
 MONTH(sale_date) month,
 SUM(total_amount) total_sales
FROM sales_clean
GROUP BY YEAR(sale_date),
         MONTH(sale_date)
ORDER BY year, month;
-- Drill-down: daily details
SELECT
 sale_date, product, city,
 quantity, total_amount
FROM sales_clean
WHERE YEAR(sale_date)=2026
ORDER BY sale_date;

Slice and dice

-- Slice: one category
SELECT *
FROM sales_clean
WHERE category='Electronics';
-- Dice: several filters
SELECT *
FROM sales_clean
WHERE category='Electronics'
 AND city IN ('Manila','Makati')
 AND sale_date BETWEEN
     '2026-01-01' AND '2026-03-31';

Quick check: Why is the second query “dice” instead of “slice”?

Pivot-style comparison

SELECT category,
 SUM(CASE WHEN city='Manila' THEN total_amount ELSE 0 END) Manila,
 SUM(CASE WHEN city='Makati' THEN total_amount ELSE 0 END) Makati,
 SUM(CASE WHEN city='Cavite' THEN total_amount ELSE 0 END) Cavite,
 SUM(CASE WHEN city='Laguna' THEN total_amount ELSE 0 END) Laguna
FROM sales_clean
GROUP BY category;

Each city becomes a column, making location comparisons easier.

HOLAPCombines cube and relational storageBalances speed and capacityMore complex to manage

04

Business Intelligence

BI combines processes and tools that turn data into useful information for decision-making.

Data›Information›Insight›Decision
Example: Transactions show Manila has the highest revenue. Management may increase stock or marketing in Manila.

From source system to decision

Sources›ETL / ELT›Warehouse›Analytics›Dashboard›Decision

BI architecture layers

  • Data source layer
  • Integration layer
  • Storage layer
  • Analytics layer
  • Presentation layer

Core components

Sources supply data. ETL or ELT prepares it. The warehouse stores it. Queries analyze it. Reports and dashboards communicate the findings.

Reports and dashboards serve different needs

ReportDashboard
Often provides detailed informationShows the most important information quickly
May contain several pagesUsually designed for one screen
Can support investigation or documentationSupports monitoring and quick decisions
May be staticOften includes filters and interaction

Metrics and KPIs

Metric

Any measurable value, such as the number of website visits.

KPI

An important metric tied to a goal, such as monthly revenue against a target.

Useful KPI examples

TOTAL REVENUEPASSING RATECUSTOMER RETENTIONINVENTORY TURNOVER

A useful KPI has a clear definition, a time period, and a connection to a decision.

Four types of BI analysis

TypeQuestionExample
DescriptiveWhat happened?Revenue decreased in March.
DiagnosticWhy did it happen?Two popular items went out of stock.
PredictiveWhat might happen?Demand may rise next month.
PrescriptiveWhat should we do?Restock before the expected increase.

Effective dashboard design

  • Give the dashboard one clear purpose.
  • Place important KPIs at the top.
  • Use charts that match the questions.
  • Apply consistent labels and colors.
  • Add useful filters.
  • Leave enough space between visuals.

Avoid

  • Too many charts
  • Decorative graphics without meaning
  • Unclear labels
  • Unnecessary colors
  • Charts that distort comparisons

LESSON 5

Performance
Optimization

Improve query speed, scalability, and resource use.

05

Why warehouse performance matters

Optimization helps queries return useful results with less time and fewer resources.

  • Faster dashboards
  • Timely reports
  • Better support for growing data
  • Lower resource cost

Common causes of delay

  • Very large tables
  • Full-table scans
  • Too many joins
  • Unnecessary columns
  • Repeated calculations
  • Poor file organization

Basic query optimization

Less efficient

SELECT *
FROM sales_clean
WHERE YEAR(sale_date)=2026;

More focused

SELECT sale_date, product,
       category, total_amount
FROM sales_clean
WHERE sale_date>='2026-01-01'
  AND sale_date<'2027-01-01';

Select required columns, filter early, and avoid calculations on the filtered column when possible.

Efficient joins and indexes

JOIN guidance

  • Join using the correct key.
  • Select only needed columns.
  • Filter data before an expensive join.
  • Remove unnecessary joins.
  • Check for duplicate keys.

Index concept

An index works like a book index. It helps locate records without checking every page.

Indexes require storage and maintenance. Databricks also uses data skipping and optimized layout to reduce the data read.

Partitioning reduces unnecessary reading

CREATE OR REPLACE TABLE sales_partitioned
USING DELTA PARTITIONED BY (sales_year)
AS SELECT *, YEAR(sale_date) sales_year
FROM sales_clean;

SELECT category, SUM(total_amount) total_sales
FROM sales_partitioned
WHERE sales_year=2026
GROUP BY category;
Avoid excessive partitioning. Small tables and columns with many unique values may create too many small files.

Storage layout supports analysis

Parquet

Columnar storage lets a query read only the required columns.

Delta Lake

Adds reliable transactions, schema checks, table history, updates, and optimization features.

If a query needs only category and total amount, columnar storage can avoid reading unrelated columns.

Pre-aggregation avoids repeated work

CREATE OR REPLACE TABLE monthly_sales_summary AS
SELECT
 DATE_TRUNC('MONTH',sale_date) sales_month,
 category,
 SUM(total_amount) total_sales,
 COUNT(*) number_of_sales
FROM sales_clean
GROUP BY DATE_TRUNC('MONTH',sale_date), category;

Dashboards can query the smaller summary table instead of recalculating the same totals from detailed transactions.

Databricks optimization tools

-- Reuse frequent data
CACHE TABLE sales_clean;

-- Release cached data
UNCACHE TABLE sales_clean;

-- Compact Delta files
OPTIMIZE sales_clean;

What they do

  • Cache: speeds repeated access but uses resources.
  • OPTIMIZE: combines small Delta files for more efficient reading.
  • Data skipping: avoids files that cannot match a filter.
  • Photon: accelerates supported SQL and DataFrame workloads when enabled.

Query plans expose expensive work

EXPLAIN FORMATTED
SELECT category, SUM(total_amount) total_sales
FROM sales_clean
WHERE sale_date>='2026-01-01'
GROUP BY category;

Inspect the plan for table scans, filters, joins, aggregations, and large data exchanges.

Measure execution time before and after a change. A change counts as an improvement only when evidence supports it.

Optimization involves trade-offs

TechniqueBenefitCost or risk
Summary tableFaster repeated reportsMore storage and refresh work
CacheFaster reuseConsumes memory
PartitioningReads fewer filesMay create many small files
More computeMay finish soonerHigher cost
PrecomputationQuick resultsLess flexibility

  3. Select only required columns.
  4. Apply a direct date range filter.
  5. Create a summary table.
  6. Test cache or OPTIMIZE where available.
  7. Run the improved query and compare.
